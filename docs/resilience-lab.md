# AstraGrid Resilience Lab

**AstraGrid Resilience Lab** is an automated experiment execution, independent evaluation, and mission-replay framework for the AstraGrid lunar habitat simulation platform.

Its primary purpose is to provide rigorous, unbiased observability and evaluation across diverse habitat operating regimes and fault conditions without assuming either the baseline heuristic controller or the rolling-horizon MILP controller is correct or optimal.

---

## 1. Core Principles & Architectural Separation

Resilience Lab operates under strict information-boundary isolation:

```
[ Scenario Schedule & Seed ]
             │
             ▼
┌────────────────────────────────────────┐
│  Habitat Simulator (Physical Truth)    │ ───► True physical state, balances, & degradation
└────────────────────────────────────────┘
             │
             ▼ (Discretized / Noisy Channel)
┌────────────────────────────────────────┐
│  Synthetic Telemetry (Observations)    │ ───► Controller-visible sensors & quantized equipment status
└────────────────────────────────────────┘
             │
             ▼
┌────────────────────────────────────────┐
│  State & Capability Estimators         │ ───► Estimated SOC, quality flags, conservative capabilities
└────────────────────────────────────────┘
             │
             ▼
┌────────────────────────────────────────┐
│  Controllers (AstraGrid MILP / Base)   │ ───► Proposed plans & candidate actions
└────────────────────────────────────────┘
             │
             ▼
┌────────────────────────────────────────┐
│  Independent Plan Validator            │ ───► Validated actions or fallback routing
└────────────────────────────────────────┘
             │
             ▼
┌────────────────────────────────────────┐
│  Simulator Advance (Execution Audit)   │ ───► Boundary execution audit & actual transitions
└────────────────────────────────────────┘
             │
      (Post-Run Only)
             ▼
┌────────────────────────────────────────┐
│  Resilience Lab Independent Evaluator  │ ───► Ground-truth extraction, metrics, replay & report
└────────────────────────────────────────┘
```

### Seven-Tier Information Architecture
1. **Physical Ground Truth**: True internal mass/energy state (`battery_kwh`, `oxygen_kg`, `water_kg`, `temperature_c`), true equipment degradation factors, and scheduled fault intervals.
2. **Controller-Visible Telemetry**: Reported sensor readings (`solar_kw`, `soc_sensors`) and quantized equipment status flags. Hidden fault factors are not leaked.
3. **Estimated State & Capability**: Telemetry-derived estimations used by controllers for decision-making.
4. **Proposed Actions & Plans**: Optimization outputs generated by controllers.
5. **Validated Actions**: Proposals approved by independent safety validation or routed to fallback.
6. **Actual Execution Outcomes**: Actual actions advanced at the simulator boundary and audited.
7. **Post-Run Evaluation Results**: Objective metrics, statistical summaries, and diagnostic annotations calculated strictly after the run exits. Evaluation truth is never fed back into running controllers.

## 2. Key Components

### 2.1 Automated Experiment Runner (`ExperimentRunner`)
- Orchestrates reproducible multi-scenario, multi-controller, multi-seed simulation batches.
- Guarantees matched controller comparisons start from equivalent scenario deep copies, initial states, and random seeds.
- Maintains independent mutable states between runs (no cross-run memory or state contamination).
- Preserves failed runs with execution diagnostics rather than silently omitting them.

### 2.2 Independent Evaluation Engine (`IndependentEvaluator`)
- Derives all metrics from actual physical transitions, the task ledger, and simulator execution audit records.
- Does not trust optimizer objective values, predicted battery trajectories, or claimed feasibility.
- Unvalidated actions executed are counted directly from execution audit evidence:
  $$\text{unvalidated\_actions} = \sum [\text{simulator\_called} \land \neg \text{validation\_accepted} \land \text{execution\_succeeded}]$$

### 2.3 Statistical Resilience Aggregator (`ResilienceStatistics`)
- Groups runs by `(scenario_id, controller)` across random seeds.
- Reports mean, median, min, max, standard deviation, and Student-$t$ 95% confidence intervals when $N \ge 3$.
- Identifies matched pairs and computes objective deltas ($\text{AstraGrid} - \text{Baseline}$) with qualitative trade-off notes.

### 2.4 Mission-Control Replay Console (`MissionReplayBuilder`)
Extracts a complete 8-panel operational inspection for every simulated timestep:
1. **Observation**: Raw telemetry readings available to the controller.
2. **Estimates**: Controller's internal state estimate and inferred capability.
3. **Proposed Plan**: Controller's proposed candidate plan and solver status.
4. **Validation Result**: Safety validator acceptance and rejection reasons.
5. **Accepted Plan**: Validated candidate or priority fallback action.
6. **Executed Action**: Action advanced through the simulator boundary (from audit log).
7. **Physical Transition**: Resulting mass/energy transition, supply balance, and end state.
8. **Deficits & Warnings**: Shortfalls, safety reserve violations, and active event flags.

### 2.5 Evidence-Based Diagnostic Engine (`DiagnosticRuleEngine`)
Applies transparent, explainable post-run diagnostic rules:
- `SOLAR_UNDERPERFORMANCE`: Solar generation below rated forecast during daytime illumination.
- `SOC_SENSOR_DISAGREEMENT`: Divergence between independent SOC sensor readings.
- `EQUIPMENT_STATUS_DEGRADED`: Telemetry reporting abnormal equipment capability.
- `BATTERY_RESERVE_PROXIMITY` / `OXYGEN_RESERVE_PROXIMITY`: Inventories within 10% of safety reserves.
- `CRITICAL_POWER_DEFICIT`: Electrical supply shortfall on critical life support.
- `TELEMETRY_QUALITY_DEGRADATION`: Sensor anomalies reducing estimation confidence.

## 4. CLI Usage Guide

AstraGrid CLI includes dedicated Resilience Lab commands under `astragrid lab`:

### 4.1 List Scenarios
List all built-in scenarios with their descriptions, durations, and scheduled faults:
```powershell
astragrid lab list
```

### 4.2 Run a Single Evaluated Experiment
Run a single scenario with specified controller and seed, saving full per-step CSV and replay JSON:
```powershell
astragrid lab run nominal_day --controller astragrid --seed 42 --output outputs/my_experiment
```

### 4.3 Matched Controller Comparison
Execute paired AstraGrid vs Baseline runs on identical initial conditions, producing comparison deltas and an interactive HTML report:
```powershell
astragrid lab compare combined_fault --seed 42 --output outputs/comparison_run
```

### 4.4 Batch Experiment
Execute a multi-scenario, multi-controller batch experiment with multiple seeds:
```powershell
astragrid lab batch nominal_day solar_array_damage combined_fault hard_deadline_under_shortage --seed 42 --seed 101 --output outputs/batch_evaluation
```

### 4.5 Regenerate HTML Dashboard Report
Regenerate or update the interactive HTML dashboard from existing saved JSON artifacts:
```powershell
astragrid lab report outputs/batch_evaluation
```

## 5. Generated Artifact Structure

Every experiment output directory contains:
```
outputs/resilience_lab/
  ├── experiment_manifest.json    # Machine-readable experiment metadata & run IDs
  ├── runs_summary.json           # Complete run records and evaluated metrics
  ├── runs_summary.csv            # Tabular run records for spreadsheet/data analysis
  ├── pairs_summary.json          # Matched AstraGrid vs Baseline comparisons & deltas
  ├── pairs_summary.csv           # Tabular paired comparison deltas
  ├── aggregate_report.json       # Statistical summaries grouped by scenario & controller
  ├── report.html                 # Standalone interactive HTML dashboard & replay viewer
  ├── per_step_history/           # Per-step time-series CSVs for each individual run
  │     ├── <run_id>.csv
  │     └── ...
  └── replay/                     # 8-panel per-step replay JSON and chronological timelines
        ├── <run_id>.json
        └── ...
```

## 6. Known Limitations & Development Status

1. **MILP Controller Under Active Development**: Empirical success or failure in benchmark scenarios reflects the realized behavior of the current rolling-horizon model. It does not prove theoretical optimality or guarantee identical behavior under unmodeled physical perturbations.
2. **Deterministic Simulator Engine**: Built-in physical transitions are deterministic. While random seeds are tracked and preserved for future stochastic scenarios, repeated runs of a scenario with the same seed yield identical physical transitions.
3. **Fault Attribution Uncertainty**: Telemetry anomalies (such as sensor bias or unmeasured power drops) are labeled as symptoms (e.g., "consistent with solar degradation"), not confirmed physical causes, preserving epistemological honesty.
